## 学习页音频缓存排查（重点记忆列表学习久了卡死崩溃）
- 用户现象：重点记忆列表学习页"学习久了会卡顿，甚至 APP 直接卡死崩溃"。问音频缓存是否有清理。
- 结论：**音频缓存有清理机制，但不是导致崩溃的主因；崩溃来自"已解码音频缓冲长期常驻"逼近 iOS 内存上限。**
- 已核实的代码事实：
  - `src/lib/audio.ts`：`audioCache` 是模块级 Map，硬上限 `MAX_CACHE_ENTRIES = 48`，FIFO 淘汰，淘汰时 `releaseElement()`（`pause + 清 src + load()`）主动释放原生解码资源；`useSpeechLoop` 有 generation 守卫、卸载 `stop()`、前后台切换清理、播放失败 retry 时 `releaseElement` 旧元素。定时器 `src/lib/timer.ts` 正常（完成即删，无堆积）。
  - `difficultOrder` 在 `App.startDifficultLearning` 中一次性 `shuffle` 后 `setState`，稳定；遍历完 `goNext` 置 `difficultDone` 弹完成页，**不无限循环**。
  - 关键设计缺陷：`ensureElement` 把 `HTMLAudioElement` 回写进 `AudioResult.el` 并**长期驻留 cache**。一旦 `preload=auto` 或播过，WebKit 解码缓冲常驻内存，直到被 FIFO 淘汰才 `releaseElement`。
    - 列表 < 48 词条时，size 永远 < 48，**淘汰从不触发，所有 el 永久常驻且全解码**（反直觉：小列表反而更占内存）；
    - 列表 > 48 时 steady-state 也常驻 48 份解码缓冲。
  - 重点记忆列表通常更长、含更多长难词/短语/句子（解码后单条约 1-3MB），且用户常一口气学完长列表（无单元完成页打断节奏），48 份常驻解码缓冲在低端 iOS 上可达 100MB+，触发系统 Jetsam 杀进程 → "卡死崩溃"。普通年级学习按单元（10-20 词）推进、每单元完成页打断，不易触顶。
- 修复方向（待用户确认）：
  - 方案 A（治本）：`audioCache` 只缓存 `{url, source}`（不含 el）；`HTMLAudioElement` 改为运行时按需创建、播放完/切题/淘汰时 `releaseElement` 释放，不长期驻留。cache 近零内存，el 用完即放。需改 `audio.ts` + `useSpeechLoop.playViaElement`（去掉对 `item.el` 的常驻依赖）。
  - 方案 B（快速止血，低风险）：`MAX_CACHE_ENTRIES` 48→16、预取深度 3→1~2、淘汰先 `delete` 引用再 `releaseElement`；保留预取元素但上限收紧。可先推一版真机验证。
- 状态：已实施方案 A（根治）。改动：`audio.ts` 的 `audioCache` 只缓存 `{url,source}`（移除 `el` 字段）、新增 `createAudioElement(url)` 工厂、`prefetchAudio` 改为临时 `<audio>` 元素预热（canplaythrough/error 后 `releaseElement`、2s 兜底释放）；`useSpeechLoop` 的 `playViaElement` 每题 `createAudioElement` 新建元素并在开头 `releaseElement(audioRef.current)` 释放上一题、`stopAll` 用 `releaseElement`、`visibilitychange` 回前台去掉 `item.el=undefined`。`tsc -p tsconfig.app.json` 与 `vite build` 均通过。已升 `APP_BUILD 35→36` 并 commit+push，待真机验证重点记忆长列表学习内存是否稳住（不再卡死崩溃）。

## 后台长时间唤醒后键盘非英文小写（需手动切换）
- 用户现象（2026-08-27 22:16）：放后台时间比较长后唤醒，键盘不是默认英文小写全键盘，需手动切回。
- 根因：iOS 在 app 从后台恢复时，对已聚焦的 input **不会重新评估 inputmode**，会直接沿用后台前的中文输入法。原 `SpellingInput` 的 `onVis`（visibilitychange）在「答题中」分支只做了 `flushSync(setInputKey+1)` 重建 input DOM，没有先让旧 input 失焦，于是 iOS 直接把后台前的中文键盘带回来。
- 修复（`src/components/SpellingInput.tsx`）：在 `onVis` 进入重建前，统一先 `inputRef.current?.blur()`（对答题中/完成态都先失焦）；答题中分支再 `flushSync` 重建 input，新 input 经 ref callback + useLayoutEffect 重新应用 `inputmode="latin"`，迫使 iOS 在 resume 时重新读取并切回英文小写。
- 验证：tsc 通过；issue 为 iOS 平台行为，需真机（TestFlight）验证。未推送（用户尚未要求升构建号）。
- 补充：`inputmode="latin"` 是 iOS WebKit 私有扩展值，冷启动首次进入靠 ref callback + useLayoutEffect 生效；后台恢复靠 blur→rebuild→focus 强制重新评估。若真机仍残留中文，下一步可尝试 focus 时加 rAF 延迟或调整 inputmode 组合。
