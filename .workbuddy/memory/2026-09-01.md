## 首遍音频音量偏小：根因判定 + 通路保温修复（本地完成，未推送，随 build 48）

### 关键实验结论（用户提供）
**「每个词的第一遍都小，同一词重播就正常」**——不是只有冷启动那一次。
→ 直接排除 H2「AVAudioSession 类别 = Ambient 走铃声音量通道」（那只会导致会话首次激活时偏小）。
→ 判定为 **H1：音频硬件通路冷启动**。词 A 播完 → 间隔 `gapMs=3000` → 通路空闲回落 →
   词 B 的 `play()` 要重新拉起硬件通路 → 开头一段落在未就位窗口 → 偏小；
   同元素立刻重播时通路尚热 → 正常。这也解释了「`load()` 清缓冲后退回偏小」。

### 实施修复
新增 `public/silence.wav`：48 kHz / mono / 16-bit / 1.5 s，220 Hz **振幅 ±1 LSB（≈ -96 dBFS）**。
- 与主流词条音频同规格（5197 个 mp3 中 65.8% 是 48 kHz），避免通路被拉到别的采样率。
- 用 ±1 LSB 而非纯 0：纯静音帧可能被 WebKit 当作「无音频输出」而不激活会话。
- **不能用 `muted = true`**（同样不激活通路）；**不能写 `volume = 0`**（iOS 只读、恒为 1，空操作）。

`src/hooks/useSpeechLoop.ts`：
- 新增 `startAudioWarm()` / `stopAudioWarm()`（模块级，全局单例 `warmEl`，`loop = true`）。
- 时序：`scheduleNext()` / `advance()` 开头 `startAudioWarm()`（间隔期保温）；
  `playCurrent()` 开头 `stopAudioWarm()`（真词开播即停）→ **两者零重叠，不混音、不 ducking**。
- `start()` 里也保温（覆盖冷启动 + 解析异步窗口）；`stop()` / 切后台 `hidden` / `speakWebSpeech()` 前停保温。
- 空闲自动停：`WARM_IDLE_MS = 8000`，每次 `startAudioWarm()` 续期。首页调 `primeSpeech()` 只是
  「解锁 + 短暂保温」，不会让静音无限期常驻；学习页每轮间隔都会续期，整段学习期持续保温。

### 顺带清理的三处死代码 / 有害代码
1. `el.volume = 1` → 删除（iOS `HTMLMediaElement.volume` 只读恒为 1，纯空操作），保留 `el.muted = false`。
2. `primeSpeech()` 的 data URL 静音 WAV → **`data` 段长度 = 0、duration = 0**，等于什么都没预热。改用 `silence.wav`。
3. `primeSpeech()` 里的 `speechSynthesis.speak(" ")` → 删除。iOS 的 TTS 跑在 **App 进程**，
   WKWebView 是**独立进程、有自己的 AVAudioSession**，App 侧 TTS 激活时被 duck 的正是 WebView 里的
   `<audio>`——不只是无效，还是首遍偏小的加害项。

## 核查：通路保温会否重新引发「学久了卡顿」（结论：不会）

背景：build 46 修的就是 iOS 媒体实例累积导致长会话卡顿，需确认 build 48 的
保温机制不会重蹈覆辙。逐项核完后**结论：不会**，新增资源全是常数级。

### 逐项结论
| 检查项 | 结论 |
|---|---|
| 媒体元素数量 | 恒定 2 个（warmEl 单例 + 主元素），远低于 iOS 6 个并发限额 |
| warmEl 是否重复创建 | 不会。`getWarmEl()` 有 `if (warmEl) return warmEl` 单例保护 |
| safeTimeout pending Map | 不累积。**warmStopTimer 用的是原生 `window.setTimeout`，不进 pending Map**（正确设计，保温无需心跳补发）；每次续期前先 clear，最多 1 个挂起 |
| 主元素复用/释放策略 | **完全未触碰**（diff 只删了 `el.volume=1` 空操作） |
| 事件监听器 | 无增删 |
| 切后台 / 离页释放 | hidden 分支与 cleanup `stop()` 均调 `stopAudioWarm()` ✓ |

元素数对比：旧版 primeEl(单例, 0 帧 WAV) + 主元素 = 2；新版 warmEl(单例) + 主元素 = 2。**一一替换，数量不变。**

### 唯一的新增代价：持续播放的功耗（不是卡顿）
warmEl `loop=true` 持续循环。按 gapMs=3000、真词约 1s 估算，**保温占空比约 75%**
（30 分钟学习 ≈ 22 分钟在保温）。持续阻止音频 DSP 进低功耗 → 电量消耗明显增加。
这是「用功耗换音量」的固有取舍，非缺陷。内存 144KB 解码缓冲常驻，常数级。

### 🔴 发现有效性 BUG（本次改动引入）：冷启动时保温被立刻取消
`start()` 中 `startAudioWarm()` 后紧跟 `Promise.all(resolveAudio).then(...)`。
`resolveAudio` 命中 audioCache 时同步返回 → `Promise.all` 在**微任务**里 resolve →
`playCurrent()` 立刻 `stopAudioWarm()` → warmEl 的 `play()` 尚未真正出声就被 pause。
**整个链条在同一个事件循环 tick 内完成，warmEl 从未真正播放过。**
- 受影响：进入学习页的第一题、`replayNow()` 手动重播 → 保温不生效
- 不受影响：词间 3s 间隔（`scheduleNext` 保温 → 3s 后才 `playCurrent`）→ **有效** ✓
  而「每个词第一遍偏小」正是词间场景，所以核心修复仍然成立。
- 建议修法：给 `stopAudioWarm()` 加最小保温时长保护（如 400ms 内不响应 stop），
  或让 `playCurrent` 等 warmEl 的 `play()` Promise resolve 后再执行。

### 预存在的小泄漏（非本次引入）：fallbackTimer 未清理
`start()` 中 `.then` 内 `if (gen !== activeGen) return;` 提前返回时没有
`safeClearTimeout(fallbackTimer)`。快速换题会挂一个 4s 的 pending entry；
触发后因 `valid(gen)` 为 false 安全退出、pending 自动 delete，**不会无界累积**。
顺手可在 return 前补一行 `safeClearTimeout(fallbackTimer)`。
