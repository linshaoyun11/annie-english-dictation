# 2026-09-16

## App Store 截图「真机外观层」—— 把浏览器截图修成真机版式

用户问：「你截的图都是浏览器里截的，有没有办法模拟 IPHONE 的截图」。

### 核心发现：旧截图有 81pt 的**系统性版式偏差**

`src/index.css` 给 `body` 写了 `padding: env(safe-area-inset-*)`，
`NumberPad.tsx` / `SpellingInput.tsx` 里还有**行内**版本。
**浏览器不支持 `env()` 取值，恒为 0**；真机 iPhone 上是 47 / 34。
⇒ 裸截图内容整体偏高、可用高度多出 **81pt**，与真机不一致
（例：创建角色页在真机上「再输入一次」被挤出视口，裸截图里却看得见）。

所以补安全区是**修正**，不是加装饰。

### 两个输出尺寸其实各自对应一台真机

| 输出 | 机型 | 状态栏 | 安全区 上/下 | 刘海 |
|---|---|---|---|---|
| 1284×2778 | **iPhone 14 Plus**（= 13 / 12 Pro Max，正是 ASC 6.5" 槽位） | 47pt | 47 / 34 | 162×30pt，底部圆角 12 |
| 2064×2752 | **iPad Pro 13" (M4)** | 24pt | 24 / 20 | 无 |

数值来源：`useyourloaf.com/blog/iphone-14-screen-sizes/` +
掘金/CSDN 的 iPhone 全系 safearea 表（两处一致）。

### 实现（`scripts/appstore_shots.mjs`）

- `applyInsets(page, dev)` 两步走：① `addStyleTag` 给 body 写死真机数值；
  ② 遍历 `[style]`，把行内 `env(safe-area-inset-*, 0px)` 文本替换成 px 再写回。
  `calc(env(...) + 38px)` 会自动变 `calc(34px + 38px)`，不必知道那个 38。
  ⚠️ 第 ② 步必须**每次截图前重做** —— React 重渲染会还原成 `env()` 串。
- `chromeSvg(dev, {inkTop, inkHome})` 画 `position:fixed` 的整屏 SVG（`pointer-events:none`、
  z-index 拉满），含刘海 / 状态栏文字 / 信号+WiFi+电池 / 手势条。
  挂在 `document.body` 下、不在 React 树里；reload 会清掉，故放在 `shot()` 里按需补。
- **前景色现场探测**（`probeLum`）：`elementFromPoint` 往上找第一个 alpha>0.5 的
  `background-color` 算亮度，决定黑/白。实测：`02/03-learn` 键盘 `fixed` 贴屏幕底 ⇒ 反白；
  `06-register` 键盘在文档流内、下方 34pt 是浅色 body 背景 ⇒ 保持黑色。与 iOS 行为一致。
- 新增开关：`SHOTS_CHROME=0`（退裸截图）、`SHOTS_OUT=<dir>`（换输出目录，用于留档两套）。

### 踩的坑

1. **WiFi 图标弧线角度必须是 ±45°**。先前写 `Math.cos(140°)` —— cos 为负，
   `sigBottom - dy` 跑到圆心下方，三条弧向下凸、糊成实心拱形（图上像个人形）。
2. **缩略图会骗人**：在预览页里「看出」键盘左右各差 8px 空隙，写了 `png_peek bars`
   一量，新旧两版都是 `x=0..1283` 铺满 —— 纯粹是圆角造成的错觉。
   **几 pt 级的判断一律量，不要看。**
3. 手势条颜色不能按页面名硬编码（会漏），必须探测。

### 新增工具 `scripts/png_peek.mjs`（无依赖，PNG 自解码）

- `scan <files>` —— 尺寸 / colorType / 体积（`colorType=6` = 带 alpha，ASC 拒收）
- `crop <in> <out> <x> <y> <w> <h> [scale]` —— 裁剪放大，核验状态栏/刘海/图标细节
  （输出恒为 RGB，顺带能去掉 alpha 通道）
- `bars <in> [hex] [tol]` —— 量某行某色的 x 覆盖范围（验键盘是否铺满屏宽）

### 复核结果

- 16 张全部合规：尺寸精确（1284×2778 / 2064×2752）、`colorType=2`、
  83–271KB、无横向溢出、失败设备数 0。
- 刘海实测宽 486px（@3x = **162pt**），居中偏差 0.5px。
- 对比页：`.workbuddy/preview/appstore-shots-chrome-compare.html`（裸 vs 真机并排，16 组）。
- 裸截图留档：`.workbuddy/tmp/shots-nochrome/`。

## 当晚：用户看过两边之后，要求「截屏改回上一个版本」

**结论：默认改成裸截图（无系统 UI、无安全区修正），外观层降级为可选开关。**

### 一个差点做错的细节

改回时不能只用 `SHOTS_CHROME=0` —— 当时 `applyInsets()` 是**无条件调用**的，
CHROME 只控制画不画状态栏，**安全区修正仍在生效**（内容会下移 47pt）。
即：`SHOTS_CHROME=0` 得到的是「第三种形态」，既不是上一个版本、也不是真机版。

若照此交付，画面与用户印象里的上一版仍有差异，容易被当成没改对。
**教训：开关的粒度要跟「用户能看出差异的最小单元」对齐**，
一个"关掉外观层"的意图其实包含两个独立效果（去掉系统 UI / 去掉版式修正），
所以要拆成两个开关。

### 改法

```js
const CHROME = process.env.SHOTS_CHROME === "1";   // 默认关
const INSETS = CHROME || process.env.SHOTS_INSETS === "1";  // 默认关；外观层强制带上
```

`applyInsets()` 开头加 `if (!INSETS) return 0;`。
`SHOTS_CHROME=1` 时自动带安全区 —— 否则内容贴顶、画上去的状态栏会压在标题上。

### 验证：渲染是确定性的（这是最有价值的一条）

用 `.workbuddy/tmp/shots-bare/` 里 3 张上一版原图做逐字节回归：

| 文件 | 上一版 | 新生成 | md5 |
|---|---|---|---|
| iphone 01-home | 227899 B | 227899 B | **一致** |
| iphone 06-register | 251843 B | 251843 B | **一致** |
| ipad 01-home | 164901 B | 164901 B | **一致** |

⇒ 同一份种子重跑，PNG **逐字节相同**。所以「回到上一版」可以直接靠重跑实现，
不必依赖图片备份；反过来，**想确认某个改动没影响画面，md5 比对就是最硬的判据**。
（`progress` 种子里有 `Date.now()`，但不影响渲染输出。）

另外验证：状态栏位置 `y=30`、手势条位置 `y=2760` 的墨迹宽度均为 **0/1284** ⇒ 系统层确已移除。
