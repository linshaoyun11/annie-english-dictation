## 创建新角色页：系统键盘遮挡两个密码输入框（B 方案修复）

**现象**：`RegisterPage` 输入密码时，iOS 系统数字键盘把两个密码 input 全挡住。

**根因**：页面用的是原生 `<input inputMode="numeric">`，调起 iOS **数字键盘**；
WKWebView 的数字键盘不会自动把焦点 input 滚进可视区（文本键盘有这个机制，
digit-only 键盘没有）。加上 `capacitor.config.ts` 里 `Keyboard.resize = "none"`，
WebView 不压缩，输入框直接被盖在键盘底下。

**为什么 B 方案能成（关键前提）**：项目里已有全局 `--kb-h` —— `App.tsx` 负责写入，
原生走 Capacitor `keyboardWillShow`，Web 端走 `visualViewport` 兜底（>60px 才算键盘）。
`ProfilePage`（`paddingBottom: calc(var(--kb-h) + 2.5rem)`）和 `PasswordModal`
（`bottom: var(--kb-h)`）早就在用。**RegisterPage 是唯一漏掉这个避让的页面。**

**改动（仅 `src/pages/RegisterPage.tsx`）**：
1. 根容器 `h-full flex-col px-6 pb-8 pt-8`
   → `h-full flex-col overflow-y-auto px-6 pt-8` + `style={{ paddingBottom: "calc(var(--kb-h, 0px) + 2rem)" }}`
   整页可滚，键盘弹起后底部按键盘高度留出内边距 = 滚动空间。
2. 头像区 `mt-5 flex-1 overflow-y-auto` → `mt-5`
   **必须去掉嵌套滚动容器**，否则外层 `scrollBy` 在里层独立滚动区上无效。
   头像网格高度改为随内容自然展开。
3. 两个 input 加 `onFocus={(e) => revealInput(e.currentTarget)}`。

**`revealInput` 的实现要点（复用模式）**：
```ts
const scrollOnce = () => {
  const kbH = parseFloat(getComputedStyle(document.documentElement)
    .getPropertyValue("--kb-h")) || 0;
  const visibleBottom = box.getBoundingClientRect().bottom - kbH - 16;
  const delta = el.getBoundingClientRect().bottom - visibleBottom;
  if (delta > 1) box.scrollBy({ top: delta, behavior: "smooth" });
};
scrollOnce();                          // 立刻：pwd→pwd2 切换时键盘已开
window.setTimeout(scrollOnce, 350);    // 键盘动画约 300ms，结束后校准
```
**必须滚两次**：`keyboardWillShow` 在动画**开始**时就写好 `--kb-h`，此刻布局还是键盘
弹出前的样子，量出来的 delta 偏小；350ms 后动画结束再校准一次才能对准。
第二次若已到位 delta ≤ 1 不会重复滚。

**未验证项**：桌面浏览器无软键盘，`--kb-h` 恒为 0，无法本机验证。
须用 iPad Safari 打开 dev server 进「创建新角色」页实测。
`behavior: "smooth"` 在 iOS 15.4+ 才支持，iOS 14 会静默降级为瞬间滚动（不影响功能）。

**备选方案（未采用，留档）**：A 方案 = 自绘数字键盘（新建 `NumberKeyboard.tsx`，
端口到 body、fixed 贴底，与学习页 A–Z 键盘同架构，密码区改 div 显示 `●●●●`）。
改动约 200 行但能根除遮挡 + 风格统一。用户选了 B。若 B 在真机上仍不稳，改走 A。

## 自绘键盘「卡顿」排查与修复（20:19）

**现象**：打字时比系统键盘慢半拍、不跟手。

**根因（不是性能问题，是事件时机问题）**：字母键与空格键用 `onClick`，
`click` 在 **touchend** 才触发；iOS 系统键盘是 **touchdown 即插入字符**。
差一个「手指接触时长」，常见 80~150ms。连打时每个字母都要等一次。

**佐证**：删除键用的 `onPointerDown`（为做长按连删），手感反而跟手 ——
用户没抱怨删除键，说明 pointerdown 在目标 WebView 上可靠。

**次因**：iOS Safari 只在元素（或其祖先）注册了 touch 类监听时，
才会在手指按下那一刻应用 `:active`。字母键原先只有 mousedown + click，
mousedown 在 touchend 才合成 → 高亮也要等抬起才出现，「按下去没反应」。

**修复**（`src/components/SpellingInput.tsx`）：
1. 字母键 / 空格键 `onMouseDown` + `onClick` → `onPointerDown` + `preventDefault()`。
   preventDefault 会抑制之后合成的 mousedown/mouseup/click，不会重复输入。
2. 键盘条外层 div 加空 `onTouchStart={() => {}}` —— 启用 iOS 即时 `:active` 的开关，
   回调本身无需做任何事。**不要删**，删了按下高亮会退回 touchend。
3. 额外收益：preventDefault 让 button 永不获得焦点，消除「按过字母键后
   再按物理空格/回车，被浏览器当成又点了一次该字母键」的隐患。

**排查过但排除的因素**（都已核实，别重复查）：
- 无 300ms click 延迟：`index.html` viewport 有 `user-scalable=no`。
- 无常驻高频开销：无 `setInterval` / `requestAnimationFrame`，
  `useSpeechLoop` 只有递归 `safeTimeout(tick, 3000)`。
- `safeTimeout` 的 `runKicks` 挂在 document 上（capture，touchstart/pointerdown），
  每次触摸都会跑，但首行 `pending.size === 0` 即返回，pending 通常 1~3 条，可忽略。
- 每次按键的 React 重渲染（约 60 节点 diff）约 1~3ms，不是瓶颈，未做 memo 化。

**未做、待用户决定**：按键音效（系统键盘有 click 音，能进一步提升跟手感，
但会与单词朗读混在一起）、下划线 `width` transition 改 transform（省一次重排）。
