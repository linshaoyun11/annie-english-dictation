## 创建新角色页：系统键盘遮挡两个密码输入框（B 方案修复）

**现象**：`RegisterPage` 输入密码时，iOS 系统数字键盘把两个密码 input 全挡住。

**根因**：页面用的是原生 `<input inputMode="numeric">`，调起 iOS **数字键盘**；
WKWebView 的数字键盘不会自动把焦点 input 滚进可视区（文本键盘有这个机制，
digit-only 键盘没有）。加上 `capacitor.config.ts` 里 `Keyboard.resize = "none"`，
WebView 不压缩，输入框直接被盖在键盘底下。

**为什么 B 方案能成（关键前提）**：项目里已有全局 `--kb-h` —— `App.tsx` 负责写入，
原生走 Capacitor `keyboardWillShow`，Web 端走 `visualViewport` 兜底（>60px 才算键盘）。
`ProfilePage`（`paddingBottom: calc(var(--kb-h) + 2.5rem)`）和 `PasswordModal`
（`bottom: var(--kb-h)`）早就在用。**RegisterPage 是唯一漏掉这个避让的页面。**

**改动（仅 `src/pages/RegisterPage.tsx`）**：
1. 根容器 `h-full flex-col px-6 pb-8 pt-8`
   → `h-full flex-col overflow-y-auto px-6 pt-8` + `style={{ paddingBottom: "calc(var(--kb-h, 0px) + 2rem)" }}`
   整页可滚，键盘弹起后底部按键盘高度留出内边距 = 滚动空间。
2. 头像区 `mt-5 flex-1 overflow-y-auto` → `mt-5`
   **必须去掉嵌套滚动容器**，否则外层 `scrollBy` 在里层独立滚动区上无效。
   头像网格高度改为随内容自然展开。
3. 两个 input 加 `onFocus={(e) => revealInput(e.currentTarget)}`。

**`revealInput` 的实现要点（复用模式）**：
```ts
const scrollOnce = () => {
  const kbH = parseFloat(getComputedStyle(document.documentElement)
    .getPropertyValue("--kb-h")) || 0;
  const visibleBottom = box.getBoundingClientRect().bottom - kbH - 16;
  const delta = el.getBoundingClientRect().bottom - visibleBottom;
  if (delta > 1) box.scrollBy({ top: delta, behavior: "smooth" });
};
scrollOnce();                          // 立刻：pwd→pwd2 切换时键盘已开
window.setTimeout(scrollOnce, 350);    // 键盘动画约 300ms，结束后校准
```
**必须滚两次**：`keyboardWillShow` 在动画**开始**时就写好 `--kb-h`，此刻布局还是键盘
弹出前的样子，量出来的 delta 偏小；350ms 后动画结束再校准一次才能对准。
第二次若已到位 delta ≤ 1 不会重复滚。

**未验证项**：桌面浏览器无软键盘，`--kb-h` 恒为 0，无法本机验证。
须用 iPad Safari 打开 dev server 进「创建新角色」页实测。
`behavior: "smooth"` 在 iOS 15.4+ 才支持，iOS 14 会静默降级为瞬间滚动（不影响功能）。

**备选方案（未采用，留档）**：A 方案 = 自绘数字键盘（新建 `NumberKeyboard.tsx`，
端口到 body、fixed 贴底，与学习页 A–Z 键盘同架构，密码区改 div 显示 `●●●●`）。
改动约 200 行但能根除遮挡 + 风格统一。用户选了 B。若 B 在真机上仍不稳，改走 A。

## 自绘键盘「卡顿」排查与修复（20:19）

**现象**：打字时比系统键盘慢半拍、不跟手。

**根因（不是性能问题，是事件时机问题）**：字母键与空格键用 `onClick`，
`click` 在 **touchend** 才触发；iOS 系统键盘是 **touchdown 即插入字符**。
差一个「手指接触时长」，常见 80~150ms。连打时每个字母都要等一次。

**佐证**：删除键用的 `onPointerDown`（为做长按连删），手感反而跟手 ——
用户没抱怨删除键，说明 pointerdown 在目标 WebView 上可靠。

**次因**：iOS Safari 只在元素（或其祖先）注册了 touch 类监听时，
才会在手指按下那一刻应用 `:active`。字母键原先只有 mousedown + click，
mousedown 在 touchend 才合成 → 高亮也要等抬起才出现，「按下去没反应」。

**修复**（`src/components/SpellingInput.tsx`）：
1. 字母键 / 空格键 `onMouseDown` + `onClick` → `onPointerDown` + `preventDefault()`。
   preventDefault 会抑制之后合成的 mousedown/mouseup/click，不会重复输入。
2. 键盘条外层 div 加空 `onTouchStart={() => {}}` —— 启用 iOS 即时 `:active` 的开关，
   回调本身无需做任何事。**不要删**，删了按下高亮会退回 touchend。
3. 额外收益：preventDefault 让 button 永不获得焦点，消除「按过字母键后
   再按物理空格/回车，被浏览器当成又点了一次该字母键」的隐患。

**排查过但排除的因素**（都已核实，别重复查）：
- 无 300ms click 延迟：`index.html` viewport 有 `user-scalable=no`。
- 无常驻高频开销：无 `setInterval` / `requestAnimationFrame`，
  `useSpeechLoop` 只有递归 `safeTimeout(tick, 3000)`。
- `safeTimeout` 的 `runKicks` 挂在 document 上（capture，touchstart/pointerdown），
  每次触摸都会跑，但首行 `pending.size === 0` 即返回，pending 通常 1~3 条，可忽略。
- 每次按键的 React 重渲染（约 60 节点 diff）约 1~3ms，不是瓶颈，未做 memo 化。

**未做、待用户决定**：按键音效（系统键盘有 click 音，能进一步提升跟手感，
但会与单词朗读混在一起）、下划线 `width` transition 改 transform（省一次重排）。

## Bug：答对后「无操作」自动跳下一题（已修，未提交/未升构建号）

**现象**：答对进入正确页，没点按钮也没按空格，有时自己跳到下一题。**偶发**。

**根因（两个缺陷叠加）**：
1. **Portal 的事件冒泡走 React 组件树，不走 DOM 树**。
   `SpellingInput` 的自绘键盘用 `createPortal` 挂到 `body`，DOM 上不在
   LearnPage 根容器内，但 React 合成事件仍沿组件树冒泡到
   `LearnPage` 根容器的 `onTouchStart/onTouchEnd`（上滑切题手势，阈值 dy < -60）。
   → 键盘上的任何抬手动作都会参与手势判定。
2. **`handleTouchStart` 用 `e.touches[0]`（当前所有触点中的第一个），
   而 `handleTouchEnd` 用 `e.changedTouches[0]`（刚抬起的那一个）**。
   多指交替打字时两者不是同一根手指，算出巨大的虚假 dy：
   拇指按 M（y=700）→ 另一指按 Q（touches[0] 仍是 M）→ Q 的手指抬起（y=620）
   → dy = 620-700 = -80 < -60 → goNext()。
   答对后 entry 已在 `completedEntryIds`，`processNow` 检查通过 → 直接跳题。

**修复（`LearnPage.tsx` + `SpellingInput.tsx`）**：
- 键盘根元素加 `data-dictation-keyboard=""`；
  `handleTouchStart` 用 `e.target.closest("[data-dictation-keyboard],button")` 排除，
  命中则 `touchStartY.current = null`（不是「不记录」，是显式清空，防残留）。
- 起点改用 `e.changedTouches[0]`（本次刚按下的那根手指）。
- `e.touches.length > 1`（按下时）与 `e.touches.length > 0`（抬起时）直接放弃判定
  —— 多指手势不参与。

**教训（通用，改手势代码时必读）**：
- **Portal 只改变 DOM 层级，不改变 React 合成事件的冒泡路径**。
  往 body 上 portal 的浮层（键盘/弹窗/Toast），其触摸/点击事件仍会到达
  逻辑父组件的 handler。写全局手势时要么在浮层内 stopPropagation，
  要么给浮层打 data 标记让上层排除。
- **touch 手势的起点必须用 `changedTouches[0]`，不能用 `touches[0]`**。
  且必须检查 `e.touches.length` 排除多指。

**排查过、已排除的方向**（别再查）：
- `autoNext` 配置：默认 `false`（`users.ts:19`），设置页可开；开着时正确页有
  「1.8 秒后自动进入下一题」提示文案，属预期行为，不是 bug。
  若用户开着 autoNext 又报此问题，先让用户确认设置页开关状态。
- `safeTimeout` 心跳补发（`lib/timer.ts` 的 `now <= scheduledAt` 判冻结分支）：
  答对后的 1800ms 定时器与 `goNext` 的 50ms busyRef 解锁定时器，
  在正常时钟下不会误补发（心跳监听跑在 React handler 之前的 capture 阶段）。
- 物理键盘空格（连妙控键盘时按空格 = 下一题）：设计如此。

## Bug：iPad 浏览器答对几个后所有词条音频无声（静态排查，根因未定论）

**现象**：iPad Safari 上答题，前几个词有声，答对几个之后**所有**词条音频无声。

**已排除的方向**（别再查）：
- 不是单个词条音频损坏（manifest 5197 条随包分发，前面能响说明文件 OK）。
- 不是 `loopRef` 卡 false：祝贺用 `frozen={celebration!==null}` 传给 LearningCard，
  `frozen` 变化时 effect 重跑，`frozen` 回 false 会重新 `startAudio()`，链是通的。
- 不是 `safeTimeout`/`timer.ts` 句柄冲突：`pending` Map 的 key 用
  `window.setTimeout` 返回值，与 `startAudioWarm` 里的原生 setTimeout 同计数器不冲突。

**嫌疑排序（待诊断数据定论）**：

1. **单元完成祝贺污染音频会话（最可疑）**：一单元 10 词条，答对几个正好触发单元
   完成 → `speech.stop()` + `playCelebrationJingle()`（`celebration.ts:74`）。
   jingleEl 复用元素先 `load()` 再 `play()`，而此刻音频会话刚被 `stop()` 拆除，
   play() 易被拒 → `p.catch(() => synthJingle())` → **`new AudioContext()`**。
   iPad Safari 上无手势创建的 AudioContext 会 suspended，且与 HTMLMediaElement
   抢同一音频会话 —— 已知会让后续 `<audio>` 全部静默。
   **时间点与症状都吻合。**

2. **`speechSynthesis.cancel()` 滥用**：`stopAll()` 与 `playCurrent()` 每次都
   无条件 cancel；iPadOS Safari 上频繁 cancel 会让语音引擎僵尸化并持有会话。
   每轮朗读（3s）一次，长会话上百次。

3. **detached `<audio>` 累积**：`createAudioElement` 的 `new Audio()` 从不插入 DOM，
   换一词新建 1 个。iOS WebKit 对同时活跃媒体会话有上限，`releaseElement`
   理论上能让它退出会话但依赖 WebKit 及时回收。build 46 已针对此优化过。

4. **预取请求占连接槽**：`LearnPage:230/249` 每切一题 `prefetchAudio` 后 3 题
   （fire-and-forget fetch，无超时/无取消）。Safari 对同域并发连接上限 6，
   dev server（HTTP/1.1）下若请求挂起会占满槽位 → `<audio>` 的 src 请求排队
   → `play()` resolve 但没数据 → 无声 + 看门狗疯狂 forceFresh 重建元素加剧堵塞。
   **只在浏览器/dev server 出现、TestFlight app 版（本地文件）不出现 —— 若用户确认
   只有浏览器有问题，此嫌疑直接跃升为第一。**

5. **保温与真词的 pause/play 竞态**：`stopAudioWarm()`（pause）后立即 play 新元素，

## 修复「首页年级卡片要点两次才进得去」（未提交，待 iPad 验证）

**症状**：首次启动登录后，首页点年级卡片要点两次才进入学习页。
（只报了年级卡片，没报「继续学习」等按钮 —— 这条是定位的关键判别依据。）

**根因推理**：
- 逻辑层排除：`startLearning` 无「首次不生效」分支；`if (!progress || !currentUser) return`
  不成立（handleLogin 同步 loadProgress 后才 setView）；`primeSpeech()` 有 try/catch。
- **click handler 一旦派发就一定会 setView**，所以要么 click 没派发，要么页面切了但渲染空。
  LearnPage 第 879 行 `if (!entry) return null` 会白屏 → 用户不会「再点一次卡片」→ 排除。
  ⇒ 结论：**iOS 没有为第一次点按合成 click**。
- **决定性线索**：年级卡片是首页**唯一**带 `:hover` 的元素（`hover:border-primary/30`），
  其余按钮（继续学习 / TabBtn / IconButton / 清空进度 / 头像）都没有。
  iOS Safari 对带 :hover 的元素会「第一次 tap 只应用 hover 态，第二次才合成 click」
  （Nicholas Zakas《iOS has a :hover problem》、CSS-Tricks《The Annoying Mobile Double-Tap
  Link Issue》）。之所以只报年级卡片，正是因为它唯一有 hover。
- 次要嫌疑（一并加固）：登录成功后 PasswordModal 连同**聚焦中的 input 被整棵树卸载**，
  是「移除而非 blur」，iOS 键盘会话不一定正常收起，残留输入状态也可能吞掉第一次 tap。
  这能解释「首次启动」这个前缀。
- 注：Tailwind v4 的 `hover:` 变体默认已包 `@media (hover: hover)`，但 iPad 上该
  媒体查询的实际取值有争议（搜索结果互相矛盾：有说 iPad 默认触控是 hover:none，
  也有说 iPad 只要"能接鼠标"就恒为 hover:hover）。所以不能只靠删 hover 了事。

**修复（3 处，tsc 通过）**：
1. `src/pages/HomePage.tsx`：年级卡片 `onClick` → **pointerdown/pointerup 自绘 tap 判定**
   （`pressRef` 记起点，位移 > 12px 判为滑动不触发，pointercancel 清空）；
   同时**删掉 `hover:border-primary/30`**；加空 `onTouchStart` 让 iOS 即时应用 `:active`。
   不调 preventDefault（否则连页面滚动一起禁掉）；不绑 onClick 故无重复触发。
2. `src/components/PasswordModal.tsx`：新增卸载 cleanup —— blur activeElement
   + `Keyboard.hide()` + 重置 `--kb-h`（覆盖登录/注册/清空进度三条路径）。
3. `src/App.tsx` `handleLogin`：切页面前先 blur + `Keyboard.hide()` + 清 `--kb-h`（双保险）。

## 「年级卡片点两次」根因修正：只有启动后第一次（推翻 hover 假设）

**用户补充的关键事实（推翻了上一版结论）**：
- 发生在 **TestFlight build 53**（我那版修复还没生效，属原始代码行为）。
- **只有启动之后的第一次需要点两次，之后每次一次就中。**
- 单点一次后**等 1~2 秒也不会自己进去**，必须再点一次。→ 不是"首次进入慢"，
  是真的吞掉了一次点击。
- 用户当前**复现不出来**，决定暂缓：代码改动保留在工作区未提交，等复现再验证。

**为什么 hover 假设不成立**：
1. 进学习页时 HomePage 是 `{view === "home" && ...}` 条件渲染 → **整个卸载**。
   回首页会重新挂载新 DOM 元素，iOS 的 sticky hover 不可能跨挂载保留，
   那每次回首页都该点两次。但用户说只有启动后第一次。
2. 用户若点过不同年级卡片，sticky hover 更解释不通。
⇒ hover 只是"年级卡是首页唯一 hover 元素"这条线索的巧合，不是根因。
   （已删 hover，无害，保留；pointerdown 自绘 tap 才是关键加固。）

**已排除（本轮新查）**：
- `startLearning`（App.tsx:291）无"首次不生效"分支，逻辑极轻：
  findResumePosition → prefetchAudio(单次 fire-and-forget) → setProgress → setView。
  handler 一旦派发必然 setView，不会静默失败。
- HomePage **没有任何 useEffect / useLayoutEffect / scrollIntoView / rAF**
  → 排除"挂载后布局位移导致第一下点空"。
- `--kb-h` 只被 LearningCard / PasswordModal / ProfilePage / RegisterPage 使用，
  **HomePage 完全不用** → 排除"登录键盘高度残留导致首页偏移"。
- 全项目无 `once:true` 监听器；window 级 touchstart/touchend/touchcancel
  （App.tsx:447，左缘右滑返回）是 `passive:true`，无法吞事件。
- `primeSpeech()` 极轻：`ensureVoiceListener()` 只挂一个空 `onvoiceschanged`，
  `startAudioWarm()` 只做 `new Audio()` + `play()`，全部 try/catch。

**剩下的候选（按"只发生一次"这一特征重排）**：
1. **登录流程残留焦点** —— 首次启动必经 UserSelect → PasswordModal（input 自动聚焦）
   → 登录。PasswordModal 带着聚焦中的 input 被整棵树卸载（是"移除"不是"blur"），
   iOS 上键盘会话/输入状态不一定正常收起，**紧接着的第一次 tap 常被 WebView 吞掉**。
   之后无焦点残留，所以后续每次一点就中。**这是唯一完美吻合"只第一次"的候选。**
   （已加的修复：PasswordModal 卸载 cleanup + App.handleLogin 切页前 blur/Keyboard.hide）
2. **首次音频解锁** —— 第一次 tap 同时是会话内首次 `primeSpeech()` → 首次 `el.play()`，
   触发 AVAudioSession 激活。可能干扰此次手势的 click 合成。只在冷启动发生一次。
3. **缺 `touch-action`** —— 全项目 **没有一处 `touch-action` 声明**（只有
   `-webkit-tap-highlight-color: transparent`）。index.html 虽有
   `user-scalable=no, maximum-scale=1.0`，但 iOS 10+ 已忽略该指令，
   现代可靠做法是元素上加 `touch-action: manipulation`（禁用双击缩放、
   消除 300ms click 延迟）。尚未添加。

**下次复现时的判别动作（按此顺序，一次定论）**：
- 看第一次点下时卡片**有没有缩一下**：
  - 无反馈 → 事件没到元素 → 候选 1（焦点）或候选 3（手势层吞并）
  - 有反馈但没进 → 与"只第一次"矛盾，需重查 setView 之后的渲染链路
- 登录进首页后，先**点一下空白处再点年级卡**：若这样就一次进，直接确认候选 1。
- 复现后优先补 `touch-action: manipulation`（成本最低、无副作用），
  再验候选 1 的 blur 是否已生效。

## 修复「答对后答对页闪一下就跳下一题」（根因确认：build 52 提速改动引入，未推送）

**根因（已确认，非猜测）**：
`SpellingInput.pushLetter` 里 `onComplete()` 是**在 pointerdown 事件处理器内同步调用**的
（SpellingInput.tsx:188-197）。字母键从 `onClick` 改成 `onPointerDown` 后：
- **改之前**：字母在 `click`（touchend 之后）才入账 → touchend 时刻词条**尚未完成**

- **改之后**：字母在 pointerdown（手指刚按下）就入账 → pointerdown 是离散事件，

  → touchend 时刻词条**已完成** → `processedNow === true` → `goNext()` 直接触发。

- `goNext` 在 LearnPage 内只有 1 个调用点（上滑手势 706 行）。

## 修复「1/2/3 行字母键列宽 0.6px 理论差」（未提交）

**根因（SpellingInput.tsx 第 441–517 行）**：
第 2 行（a-l）的 2 个缩进 `<span flex-[0.5]>` 让 flex container
多 1 个 gap。每行字母键宽公式：
- 第 1 行 = (W − 9g)/10
- 第 2 行 = (W − 10g)/10   ← 多 1 个 gap，损失 0.6px（g=6 时 = 6/10）
- 第 3 行 = (W − 9g)/10    ← 与第 1 行已经严格相等

第 1 行和第 3 行已经是 0 误差，**只有第 2 行有 0.6px 缩**。

**修法（不改键高/间距/圆角/第 4 行）**：
- 第 2 行 row div 加 inline style（仅 ri===1 时）：
  `paddingLeft/Right: calc((100% + 6px) / 20)`
- 数学证明 letter 严格相等：
  p = (W + g) / 20
  第 2 行 letter 宽 = (W − 2p − 8g) / 9
                  = (W − (W + g)/10 − 8g) / 9
                  = (9W − W − g − 80g) / 90
                  = (8W − 81g) / 90
                  = (8(W − 10g) + 8g − 80g + 81g − 81g) / 90  ... 简化：
                  实际 = (W − 2·(W+g)/20 − 8g) / 9
                      = (W − (W+g)/10 − 8g) / 9
                      = (10W − W − g − 80g) / 90
                      = (9W − 81g) / 90
                      = (W − 9g) / 10  ✓
  与第 1 行（项目数 10 = 9 gap）严格一致。
- 删掉 `{ri === 1 && <span flex-[0.5]>` 左侧缩进
- `{ri === 1 || ri === 2 && <span flex-[0.5]>` 改为仅 `{ri === 2 && ...}`（右侧仍属第 3 行）

**为什么用户在 cb_summary 截图里还看到"按键大小不一样"**：
1.jpg (系统) 与 2.jpg (自绘) 的整体差异主要是：
- 系统 4 行 + 1 行（地球 + 语音）= 5 行；自绘 4 行（无 5/行）

- 圆角 5 vs 9（用户指令）
- 缺 shift / 123 / return / 🌐 / 🎤（用户指令省略）

本次**只修列宽理论差**，其它有意为之的差异保持原状。

   （z 左偏移 = letter+g，a 左偏移 = (W+g)/20，差 = (W+g)/20 ≈ 0.5 键宽），
   与 iOS 原生阶梯 Q→A→Z 逐行右移**一致**，不是「偏左、方向相反」。

## ⚠️ 新发现：capacitor.config.ts 有 2 个废弃字段，且长期未被 tsc 覆盖

- `ios.minVersion: "14.0"` —— Capacitor 8 **已移除**该字段（2.x/3.x 时代遗留）。
  iOS 最低版本由原生模板的 Podfile / Xcode 工程决定，配置文件改不动。
- `bundledWebRuntime: false` —— 同样已移除（Capacitor 5 起 runtime 自动注入）。
- 两者**都被 cap sync 静默忽略**，所以「删除 = 零行为变化」。已删并留注释说明。
- **为什么一直没暴露**：`tsconfig.node.json` 的 `include` 原来只有 `vite.config.ts`，
  `capacitor.config.ts` 不在 `tsc -b` 检查范围内。**已加入 include**，
  以后配置字段写错会被 tsc 直接报错（实测 `npx tsc -b --noEmit` 现在覆盖它）。

## 新增：TestFlight 包可被 Safari Web Inspector 调试

`capacitor.config.ts` 的 `ios` 段加 `webContentsDebuggingEnabled: true`。
Capacitor 4.8.0+ 该项**默认 false**（仅 development 构建可调试），即之前所有
TestFlight 包都无法用 Safari Web Inspector 连接 —— 真机问题只能靠猜。
开启后配合 `ios-webkit-debug-proxy`（Windows）即可远程调试 iPad 上的 app，
对排查「iPad 音频无声」这类问题是决定性的。只影响可调试性，不改运行时行为。

## 本地构建冒烟的坑（会重复遇到）

`npm run build` 在本机**必然失败**于清空 dist：沙箱 safe-delete 保护拦截
（dist 下 5205 个音频文件 > 阈值 50，报 SAFE_DELETE_BULK_CONFIRM_REQUIRED）。
**绕法：`npx vite build --emptyOutDir=false`**（不清空直接写入，实测 2m45s 通过，
产物正常）。CI 上无此保护，不受影响。
校验 capacitor.config.ts 单独用：
`npx tsc --ignoreConfig --noEmit --module nodenext --moduleResolution nodenext --target es2023 --skipLibCheck capacitor.config.ts`
（注意必须加 `--ignoreConfig`，否则 TS5112；`--types node` 会导致字段校验不准，别加）
