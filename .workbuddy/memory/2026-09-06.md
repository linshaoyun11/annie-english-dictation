## iPad Safari 强缓存踩坑（20:15）

用户测试 dev server 反馈祝贺页奖杯**还是米黄背景**，但本地 PNG 已经抠图。

### 排查

curl `http://127.0.0.1:5173/src/assets/trophy-celebration.png`：

```
mode: RGBA size: (1024, 1024)
tl pixel: (0, 0, 0, 0)   ← 已经透明
```

**后端 PNG 是透明的**，HMR 时间戳也更新了（`?t=1788694672346`），
但**浏览器侧仍命中磁盘缓存**。iPad Safari 对静态资源的强缓存很顽固，
即使 URL 加了 `?t=戳`，旧 PNG 仍会从 disk cache 返回。

### 解法

**改文件名让旧 URL 完全失效**（不是清缓存）：

- `src/assets/trophy-celebration.png` → `trophy-celebration-transparent.png`
- `TrophyIcon.tsx` import 路径同步更新
- 旧文件 `rm` 掉（vite 自动发现）
- git 状态：`D trophy-celebration.png` + `?? trophy-celebration-transparent.png` + `M TrophyIcon.tsx`

### 教训（已写进 memory）

**改 PNG 类静态资源想清缓存时，改文件名比"加 ?t=戳"更可靠**。
Vite 会按文件内容生成 hash，但浏览器 disk cache 对 query string 的命中判断
不完全可靠，iOS Safari 尤甚。改文件名是 100% 失效路径。

iPad 测试流程：改文件名 → dev server HMR 自动 reload → 用户关闭再开 Safari tab。

## ⚠️ 22:13 重大更正：Codemagic 触发机制，此前一直记反了

用户问「之前都是我手动点构建的，现在不用点了？」——查证后发现是我错了。

### 真相

官方文档（codemagic-yaml-cheatsheet）原文：

> `triggering`: defines the events for automatic build triggering and watched
> branches. **If no events are defined, you can only start builds manually.**

且：项目根目录有 `codemagic.yaml` 时，**Codemagic 网页端
App settings → Build triggers 里的勾选项会被完全忽略**，只认 yaml。

查 `codemagic.yaml` **全部 20 个历史版本，triggering 行数均为 0**
⇒ 本项目**从未配置过自动触发**，一直只能手动点。与用户经验完全一致。

### 之前错在哪

记忆里长期写着「无 `triggering` ⇒ 任何 push 都触发构建」——**因果关系说反了**。
这条错误规则至少影响了 4 处决策（2026-09-01 / 09-03 / 09-04 的"不 push 理由"），
推导出的「攒着一起推」结论虽然仍正确（省构建时长），但**理由是错的**。

### 已修

`d07dece` 补上 triggering：

```yaml
triggering:
  events:
    - push
  branch_patterns:
    - pattern: main
      include: true
      source: true
  cancel_previous_builds: true
```

只监听 main（避免其他分支白烧时长）；`cancel_previous_builds` 防连续 push
出两个同 build 号的包被 ASC 拒。APP_BUILD 保持 58（尚未构建过）。

### 已同步更正的位置

- `.workbuddy/memory/MEMORY.md`（构建与配置段）
- `.workbuddy/memory/topics/build-config.md`
- `.workbuddy/memory/2026-09-06.md` 两处（加删除线标注，保留历史）

### 教训

**"没有配置"不等于"用默认行为"，要先查文档确认默认值是什么。**
这次凭印象写了「无 triggering = 全部触发」，实际是「无 = 不触发」。
涉及 CI 触发/计费/发版这类有实际成本的行为，必须查官方文档原文，
