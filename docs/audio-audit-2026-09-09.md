# 音频 ⇄ 文本 错位事故核查报告

日期：2026-09-09　｜　结论：**问题属实，已修复并全量重生成**　｜　APP_BUILD 76 → 77

---

## 一、现象

用户报「人教版三年级起点 G3U1，显示 `name`，听到的却是 `point`」，TestFlight 复现。

## 二、铁证

`public/audio/manifest.json` 中 `name` → `wy-g1u2e0020`，播放的是 `wy-g1u2e0020.mp3`。

把该文件解码成 PCM，与「重新合成的文本」做归一化互相关：

| 比对对象 | 相关度 |
|---|---|
| 与**有道 "point"** | **0.9994** |
| 与 有道 "name" | 0.2749 |
| 与 Edge "point" | 0.3175 |
| 与 Edge "name" | 0.0891 |

> 判据自检：同一个文件转码后自比 0.9965（对转码免疫）；正确匹配 ≈1.000；异词 <0.35。
> 0.9994 意味着**这个文件的波形与「有道念 point」几乎完全重合**。

**结论：文件里念的就是 point，却挂在 name 名下。用户报告完全属实。**

## 三、根因（结构性，不是偶发）

音频文件以 **entry.id 命名**（`wy-g1u2e0020.mp3`），App 端播放链路是：

```
manifest[文本] → entry.id → public/audio/{id}.mp3
```

而 entry.id 由 `mk()` 的**全局递增序号**生成。词库只要重建一次（G4–G9 重建、
v22 换 SL 词表、v23 废弃去重），序号就整体位移，存量音频立刻与词表脱节。

叠加多个"补齐音频"脚本（`fill_*` / `fix_*`）各自用**两个列表按下标配对** text 与 id，
进一步引入错位。

⇒ 只要文件名依赖 entry id，这个问题**必然复发**。

> 为什么之前说"已 100% 排除错位"是错的：那次只验了 `text → id → text` 往返自洽，
> 两个方向用的都是**当前**词表，当然自洽。真正要验的是 **mp3 文件内容**。

## 四、修复

1. **文件名改为 `t + blake2b(归一化文本, 8 字节)` 哈希**，与 entry id 彻底解耦。
   生成时 text 与 out_path 在同一次函数调用内绑定，**结构上不可能再错位**。
   App 端逻辑不变（manifest 的 value 直接当文件名用）。
2. 按**当前运行时词表**全量重生成：4865 个唯一文本 × 美/英 = **9730 个文件**
   （有道优先；失败 / <1KB / >60KB 走 Edge 兜底）。
3. 删除旧命名文件 15829 个，`public/audio` 体积 412M → 194M。
4. `src/lib/audio.ts` 仅加注释说明 manifest value 已非 entry id。

## 七、排查过程中让自己误判的两个坑（重要）

| 坑 | 表现 | 误判幅度 |
|---|---|---|
| **只用一个音源做参照** | 存量库混了有道(64k/48kHz)与 Edge(48k/24kHz)，跨音源同词的相关度只有 **0.20–0.32** | 把"音源不同"全判成"词错"，错误率虚报成 **58%** |
| **用小写 key 去合成** | 有道对 `ben` / `Ben` 返回**不同录音**（9206 vs 8640 字节） | 错误率虚报成 **35%** |

修正后（双音源 + raw 原始大小写）才得到上表 9% / 14.7% 的真实值。

> 附：归一化互相关在窗口方差趋零时（长音频的静音段）会爆炸到几十上百，
> 必须按 RMS 阈值作废低能量窗口，否则会把"不相同"误判为"相同"（漏判）。

## 九、铁律

- 音频文件名**永远不要**用 entry.id，只能用文本哈希。
- 补齐音频的脚本里，text 与 out_path 必须在同一次调用内绑定，**禁止两个列表按下标配对**。
- 验证音频正确性前先做判据自检：转码鲁棒性 + 跨音源基线 + 大小写。
- 说"已排除错位"之前，必须验证 **mp3 文件内容**，光查映射自洽没有意义。
